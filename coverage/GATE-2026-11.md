## The findings

### 1. card-stream staging silently falls back to internal SRAM (second-1.json, medium)

Verdict: CONFIRMED, FIXED.
`src/net/web_admission.cpp` `stagingGet()` tried PSRAM and, on exhaustion, silently took
`MALLOC_CAP_8BIT` (internal SRAM): 2872 B per in-flight stream (`kCardStreamBuf`) out of
the pool a live turn's TLS handshake needs a contiguous block of, with no admission gate
and nothing bounding concurrent streams.

Fix: the fallback is gated on the new portable rule
`nimbus::net::cardStagingInternalOk(psramInstalled)` (`lib/core/include/nimbus/net/card_stream.h`):
a board with PSRAM never stages from internal SRAM - an exhausted PSRAM answers null and
the stream WAITS (the class-tested null-alloc path in `lib/core/src/net_card_stream.cpp`
`fillOne`, pinned by `test_no_staging_memory_waits_inside_the_budget`). A no-PSRAM board
keeps the fallback: internal SRAM is the only pool there.

Evidence (failing first): `test/test_card_stream/main.cpp`
`test_staging_never_drains_internal_on_a_psram_board` fails on the old seam
("stagingGet's internal fallback must be gated on the PSRAM rule"), passes on the fix.
Raw red/green runs on disk in the session log; the battery re-runs the suite.

### 2. sfx task 12 KB stack margin rests on a BENCH never run (second-1.json, low)

Verdict: PARTIALLY REFUTED, remainder OPEN HARDWARE.
The claim "no release-gate or host test asserts a floor on it" is partially wrong:
`tests/hil/test_l31_sram_headroom.py` already carries (a) a deterministic source guard
(`test_sfx_stack_stays_reduced`: `kSfxStackBytes` must stay <= 12288) and (b) a live
high-water floor (`RUNTIME_MIN_FREE = 2048`, exactly the BENCH note's ">2 KB") asserted
on `mem.sfxStackMin`/`mem.musicStackMin` whenever the device surfaces them. The
constant did not change in the reviewed diff, and the new work on that stack
(`playReply`'s `SpeakerTurn` wait, the CueGate queries) adds no recursion depth.
What stays open: the BENCH measurement itself - a real spoken MP3 reply's stack
high-water on hardware. NOT RUN, twice over: no bench unit exists (LAUNCH-5.0.0.md
ruling 7) and the owner's silent order forbids playing any sound. OPEN HARDWARE until
both lift; the release notes must say voice changes shipped without hardware proof.

### 3. SpeakerTurn::take() grants a phantom turn when the mutex allocation fails (second-1.json, low)

Verdict: CONFIRMED, FIXED.
`src/sfx/speaker_turn.cpp` `take()` returned true with `held_ = false` when
`xSemaphoreCreateMutex()` failed at first use - both tasks then read the DMA figures
and opened the speaker (the 1 Nov 2026 Lumi failure class), and the magic static cached
the null forever.

Fix: creation is retried (a heap-exhausted first use is recoverable; the retry race
between the sfx and music tasks is settled by a lock-free compare_exchange, the loser's
creation leaks a few dozen bytes once), and a null lock REFUSES: `take()` answers true
only when the mutex is really held.

Evidence (failing first): `test/test_sfx/main.cpp`
`test_the_speaker_turn_refuses_when_it_holds_nothing` (a source pin; the seam is
Arduino-only) fails on the old seam ("take() must refuse when the lock cannot be had"),
passes on the fix. The stack behavior itself is OPEN HARDWARE (see finding 2).

### 4. nimbusd never resets the persisted getUpdates offset when the bot token changes (second-2.json, high, the lane's top item)

Verdict: CONFIRMED, FIXED.
`nimbusd/src/telegram.h` loaded the bare offset unconditionally and persisted it after
every cycle; nothing recorded which bot it belonged to, so a rotation to a different bot
silently skipped every message forever (getUpdates above the new bot's ids answers ok
with an empty result). The device had fixed the same class for live swaps
(`src/agent/telegram.cpp`, cursor reset); nimbusd had no equivalent.

Fix: the offset file now carries the bot it belongs to - `"<offset> <bot id>"`, the id
half of the token (`nimbus::core::tgBotIdOf`, new in
`lib/core/include/nimbus/telegram_offset.h`; public by design, never the secret). On a
mismatch (a different bot, or a pre-fingerprint file from an older daemon) the offset
resets to 0: Telegram re-serves at most the one unconfirmed page. The same bot with a
rotated secret keeps its offset (update ids continue on that bot).

Evidence (failing first): `nimbusd/tests/test_telegram.cpp` section 6 - on the old
seam 6 checks fail (offset 4821 kept for a different bot; the pre-fingerprint file
trusted; the poll asks offset=4821), on the fix 26 checks pass. The class helper is
property-tested in `test/test_telegram_offset/main.cpp` `test_bot_id_of_token` (every
well-formed shape yields the id, every malformed shape yields 0, same bot across
secrets, different bots differ).

### 5. hasStanding counts owner-default routines as standing for ANY chat (second-2.json, low)

Verdict: CONFIRMED, FIXED.
`src/agent/loops_subsystem.cpp` `hasStanding()` matched `l.chatId.empty()` against any
chat, but an owner-default loop delivers to the owner's Telegram (or the web chat), so
for a member's chat it silenced the promise check (`orch_reply_guard.cpp` skips Report
cues when `laterWork_ == Standing`) for a report that never reaches them.

Fix: `hasStanding()` now uses the same delivery rule a fire uses
(`deliveryFor(l, world).target == chatId`, `resolveDelivery` from
`lib/core/src/orch_loop_delivery.cpp`): a loop counts as standing exactly for the chat
it delivers to - the owner's Telegram, the web chat fallback, its own pinned chat, or
nothing (a revoked chat).

Evidence (failing first): `test/test_loop_delivery/main.cpp`
`test_standing_follows_the_delivery_target` (the class, swept over four world shapes,
with the pre-fix rule run as the counter-model) plus
`test_hasstanding_uses_the_delivery_rule` (a source pin on the seam, which is
Arduino-only). The pin fails on the old seam, both pass on the fix.

### 6. nimbusd /api/loops and /api/wakeups POST return ok:true even when the id does not exist (second-2.json, low)

Verdict: CONFIRMED, FIXED.
`nimbusd/src/web_api.h` `loopPost`/`wakeupPost` discarded the false return of
`approve`/`setEnabled`/`cancel` and answered `{"ok":true}` unconditionally - a success
reported for a no-op on a stale list row.

Fix: the synchronous write's answer carries the real result: `{"ok":false}` when the
id misses. (`setAskFirst` returns void and stays `{"ok":true}`.)

Evidence (failing first): `nimbusd/tests/test_webapi.cpp` `checkRoutines` - on the old
seam 7 checks fail (every missing-id action answered ok:true, the second delete too),
on the fix 64 checks pass.

### 7. The Telegram dedup source tag is not namespaced by bot (second-2.json, low)

Verdict: CONFIRMED, FIXED.
A turn's dedup tag was `tg:<newest update_id>x<count>`
(`lib/harness/src/turn_inbox.cpp`), but update ids are per-bot: after a token rotation
the new bot's ids restart low, and any (id, count) matching an old-bot row still in the
chat's 48-row window was silently dropped by the H7 dedup (`engine.cpp`
`sourceSeen`) - no turn, no reply, one log line.

Fix: the tag is now `tg:<bot id>:<newest id>x<count>`, the bot id from
`nimbus::core::tgBotIdOf` of the serving token (the device passes it at
`src/agent/telegram.cpp` `noteHistory`; nimbusd's hosted photo path clears src anyway
and passes 0). Old rows carry the un-namespaced shape, which no new tag can equal.
Upgrade edge, accepted: the one page in flight across the firmware update can replay
once (at-least-once, the documented restart contract).

Evidence (failing first): `test/test_harness_history/main.cpp`
`test_source_tag_is_namespaced_by_bot` - the property (every bot pairing: same bot
stable, different bots differ) and the consequence (the old bot's row stored, the new
bot's same-id message runs, its own replay drops). With the namespace removed the
engine-level check fails; with it, 23 cases pass.

### R1. The wake-up card still renders "Approved."/"Denied." when the POST answers {"ok":false} (low)

Verdict: CONFIRMED, FIXED.
The F6 fix made the API honest (`{"ok":false}` for a missing id) but the page never read
the field: `wkPost` resolved through `jok()`, which only guards the HTTP status (200 is
`r.ok`), and `run()` renders `opts.ok(res)` whenever the promise resolves - so the
approve/deny handler answered "Approved."/"Denied." unconditionally and the owner was
told a success for a no-op (the stale-row case: the wake-up fired and was auto-removed
between the page's GET and the click). Verified at `51db0368`:
`include/web/ui_js.h` `wkPost`/`act` (the generated `nimbusd/src/webui_page.h` mirrors
it), against `nimbusd/src/web_api.h` `wakeupPost` answering 200 `{"ok":false}`.

Fix, at the seam so the class is closed (not one button, not one caller): `wkPost`
itself rejects with `WK_GONE` when a 200 body says `ok:false` - no caller of the seam
can render a success state for a no-op again. The card's error handler maps it to
"That wake-up is no longer pending." and reloads the list (the stale card clears); the
policy handler maps it to "That save did not apply - try again." The device firmware
always answers `{"ok":true}` here (staged mutation, `src/net/webui.cpp`), so on-device
behavior is unchanged. Checked the other `/api/loops` page call sites for the same
class: the create form already reads `x.ok`, and the row buttons (pause/resume/delete)
render no success claim at all and reload to the truth, so neither needed a change.

Evidence (failing first): `tools/webui_harness/tests/72_wakeups_safety.spec.mjs`
"a stale approval (ok:false) is surfaced, never 'Approved.' or 'Denied.'" - red on the
old seam in both projects (desktop + phone: `2 failed`, the message was "Approved." in
the ok state), green on the fix (`8 passed`). The spec covers both verbs and asserts
the feedback state is never `ok`. The page change flows through the blessed
`tools/webui_page.snapshot` (re-blessed intentionally, `webui_concat_check.py --bless`)
and the regenerated `nimbusd/src/webui_page.h` (`nimbusd/tools/gen_webui.py`); the
full web-app suite re-ran green (651 passed, 5 skipped, 0 failed).

No finding was rejected in this pass: the single item was confirmed and fixed.

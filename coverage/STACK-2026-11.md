# Lane STACK coverage: the Telegram poll task's worst-case stack

Branch `lane/p18-STACK`, base main `7631b6a2`. Task: `lanes/STACK/TASK.md`. Written
2026-11-08 (UTC, `date -u`). Silent mode held throughout: no audio of any kind. No device
was opened, flashed or probed and Lumi was never contacted; the bench low-water is OPEN
HARDWARE (section 8). Evidence paths below are under `program-2026-10-18/evidence/`.

## 1. Why

Lumi (v4.9.0, boot 14, 8 Nov) logged `tg_poll stack: min free 936 B of 24576 (worst)`
after one voice note that ran STT, a Mistral round cut at 4125 tokens and retried, a
claim-check correction round and a routine create
(`tgstall-lumi-20261108T141614Z/nimbus.log` lines 103-122). The 29 Oct crash `2419bf4a`
aborted on the same task (`crash-2419bf4a/DECODE.md`). tg_poll runs the whole turn: the
long poll, every head round, every tool, STT, media, the staged OTA check and install,
and the Telegram archive.

## 2. Method: the gate measures the built image

`tools/release_gate/check_tg_poll_stack.py` with its reviewed rows in
`tools/release_gate/tg_poll_stack.json`; host tests in `test_tg_poll_stack.py`.

- **Frames.** Every windowed function's `entry a1, N` in the ELF. On an instrumented
  build of `7631b6a2` (`-fstack-usage -fcallgraph-info=su,da`, code unchanged) the `.su`
  numbers equal the `entry` numbers (pollTask 4944 B in both), and the ELF also covers
  the precompiled ESP-IDF libraries that no `.su` describes. ROM functions come from the
  chip's ROM ELF (`tool-esp-rom-elfs`).
- **Decode.** `.xt.prop`/`.xt.lit` are stripped first (with them, objdump prints
  mbedTLS, lwIP and newlib as data). objdump decodes linearly and loses step after the
  alignment padding that may follow an unconditional jump. Every stretch whose real
  entry (a branch target of reachable code, or a landing pad that `.eh_frame` and the
  LSDA list) objdump did not decode as an instruction start is decoded again from that
  entry, in one batched objdump run, until it meets the linear decode (section 6).
- **Calls.** `call8`; the `-mlongcalls` form (`l32r aN, lit` then `callx8 aN`); a `j`
  or `jx` into another function (ROM trampolines, tail calls). Indirect calls, in order:
  a config rule (function pointers, hooks main.cpp registers, library tables); a
  `std::function` call by exact signature, narrowed by the field it is called through or
  the lambdas created up to three calls above; a virtual call by vtable slot, narrowed by
  the receiver's declared class and the hierarchy the source line names. Code that only
  runs on another task (web server, BLE, relay) is never an indirect target. An indirect
  site nothing resolves is charged 512 B.
- **Recursion.** Depth-first from `vPortTaskWrapper -> pollTask`; every back edge is
  cut and must be declared: real recursion with a depth bound (each function on it is
  counted that many times), or an impossible cycle with why. An undeclared cycle fails.
  A VLA or alloca needs a bound or fails.
- **Fixed costs.** 544 B: coprocessor save area 320, TLS block 16, one interrupt
  exception frame 208.
- **Inline chains.** Where `.debug_aranges` misleads BFD addr2line, the chain comes from
  GDB (`list *ADDR`); with GDB missing in that case the gate fails.
- **Verdict.** The worst case from the task entry, and per named path (the worst chain
  through it): each must leave 4096 B of 24576. Exit 1 on any path under the floor or
  any analysis error. A config row an image does not use is a warning (four release
  images share the config).

Over-approximations, so the numbers are upper bounds: unresolved indirect calls at
512 B; `std::function` resolution by signature is context-insensitive; the HeadStep
wrapper row counts each cyclic HeadStep handler three times (the runHostLoop step
handler, 256 B, is counted 768 B); `exchange <-> meterCancelledJob` counts both twice.
An image older than the working tree must be analysed with `--sources <its checkout>`:
virtual calls resolve from the source line, and today's lines misresolve an old image
(this happened to the first before-run; section 7).

## 5. What changed (no stack size change, no new task, no TLS session, no NVS key)

- `src/agent/telegram.cpp`: the drained reply (`PendingReply`, 4134 B) lands in one
  PSRAM slot allocated in `begin()`; `send()` and `injectMessage()` build their queue
  items (`PendingReply`, `InboundMsg`, about 4.1 KB each) in PSRAM (`PsramItem`);
  `holdTyping` and `drainMedia` are `noinline`, so their buffers leave pollTask's frame.
  pollTask: 4944 B to 672 B.
- `src/sys/config_nvs.{h,cpp}`: `nvsGetStr` reads through `nvsReadStr` (one read-only
  handle under a mutex, the value into a PSRAM buffer) instead of
  `Preferences::getString`, whose stack array is as long as the value (up to 4000 B).
- `lib/harness/src/engine.cpp`: runTurn's large locals in one heap block
  (`RunTurnLocals`), and `TurnSources`, `TurnDebugEv` and the held `ApplyDeps` boxed:
  2912 B to 1296 B.
- Head loop and providers: `RoundRecovery`, `HeadLoopHooks`, `HeadOutcome` (runHostLoop,
  runFabricLoop), the round's `HeadStep` (runHeadLoop), `HttpRequest` and the cancelled
  meter's state (wire.h), `ProviderDeps` (cumuloAttempt, the Z.ai host) on the heap;
  helpers that run before or after a round's request, never under it, are `noinline`
  (`antLoopBody`, `antReadRound`, `antShotBody`, `antReadShot`, `refitToBudget`,
  `sendFinalBack`, `sendProseBack`, `RoundRecovery::overflowRetry/noteCut/served`,
  `typeStep`, and the photo upload's body in `uploadBody`). runHeadLoop 976 B to 480 B,
  runHostLoop 672 B to 240 B, orchTurnAnthropic 736 B to 512 B, antUploadImages 640 B
  to 400 B.
- Scheduler: `dream::fire` and the console drill box `NightDeps`/`NightResult` and the
  loop record and fire request; `checkDue` boxes its fire request and outcome. dream::fire
  656 B to 160 B, checkDue 544 B to 368 B.

Heap cost. Everything boxed inside `runTurn` is allocated under the turn's
`PsramFirstScope`, so it lands in PSRAM; the telegram queue items and the NVS read buffer
are explicit PSRAM. The scheduler boxes sit outside a turn and use internal heap for the
fire only: at most 248 B (checkDue: `LoopFireRequest` 112 + `FireOutcome` 136) plus 500 B
(dream fire: `NightDeps` 196 + `NightResult` 304), freed when the fire returns, against
an internal heap of about 30 KB free (10 KB minimum). Static DRAM: freenove-28 89947 B
(7631b6a2: 89915 B, +32 B; ceiling 91723), nimbus-tft 89867 B (ceiling 91635)
(`stack-2026-11/static-dram-*.txt`).

## 6. Two findings on the way

**The 64-level reply parse.** `kResponseNestingLimit` (64, http.h) bounds the provider
reply parse, which ArduinoJson runs recursively on tg_poll: 112 B per kept level, about
7 KB at the limit. The comment in http.h said the parse stayed well below the stack; it
is corrected. The limit is deliberate (connector payloads nest deep) and stays; the gate
counts all 64 levels, which is why the reply parse is the deepest path after the fix. A
reply nested past what the floor leaves would now be caught at build time, not on a
device.

**objdump out of step.** The first analyzer read objdump's linear decode as is. After an
unconditional jump, alignment padding put it out of step until it met a real boundary,
so it read padding and the first bytes of real code as other instructions. On
`7631b6a2` that invented a `call8` from a landing pad in a runTurn lambda to `runTurn`
itself, a cycle that does not exist (an analysis error), and it hid real calls: the
resync found `std::stable_partition`'s recursion (router catalog, at most 512 rows, 10
levels) and `sdCommand`'s one nested `APP_CMD` call, both now declared, and 1360 B of
real depth on the worst case (the `a1714f69` image: 19104 B used read linearly, 20464 B
with the resync, `stack-2026-11/resync-ablation-a1714f69-{linear,resync}.log`); the
noinline pass then brought the worst case to 19792 B. On the `7631b6a2` image
15111 stretches are decoded again, and 40 sampled ones match objdump started at the same
entry. Host tests cover the landing pad case (an invented call goes, the real
long call stays), the eh_frame/LSDA parse, live branch targets and a real objdump decode
at the stretch's address.

## 7. Failing first

On `7631b6a2` the gate exits 1: 9 paths under the floor, worst 28768 B used
(`stack-2026-11/before-7631b6a2-esp32s3-cyd.log`). The image is `7631b6a2` built with
`-fstack-usage -fcallgraph-info=su,da`, which change no code. The first before-run read
today's sources for that old image and resolved the head round's transport call through
a line that had moved (it under-counted the reply parse path at 18320 B); `--sources`
fixed that and the table above uses it. On the lane head it exits 0 on both images. It is
wired into `tools/release_gate/run_gate.py` (host gate) and `.github/workflows/release.yml`
(every release variant, after the static DRAM check), and `test_tg_poll_stack.py` runs it
on the built esp32s3-cyd and esp32s3 images in the battery.

## 2. Root cause

`NetworkManager::hostByName` (arduino-esp32 core, NetworkManager.cpp:81-86) keeps two
file-local statics (`hasGlobalV6`/`hasGlobalV4`) and, when the interface IP state just
changed, calls the RAW lwIP `dns_clear_cache()` at line 84 WITHOUT holding the TCPIP
core lock. `dns_clear_cache` (dns.c:409-419) synchronously fires `dns_call_found` for
every in-use DNS entry, and `dns_call_found` (dns.c:1071) invokes the entry's
registered callback in the CALLER's context. With SNTP's lookup pending (kicked on the
rejoin up edge by `sntpTick` -> `restartSntpClient` -> `esp_sntp_init` ->
`sntp_request` -> `dns_gethostbyname(..., sntp_dns_found, ...)`), that callback chain
re-enters raw lwIP: `sntp_dns_found` -> `sntp_try_next_server` -> `sntp_request` ->
`dns_gethostbyname` -> `dns_alloc_random_port` -> `udp_new_ip_type`, whose
`LWIP_ASSERT_CORE_LOCKED()` (udp.c:1278) fails because the relay task is not the lock
holder. The assert is `sys_thread_tcpip(LWIP_CORE_LOCK_QUERY_HOLDER)`
(lwip port lwipopts.h:54): only the task that ran `LOCK_TCPIP_CORE()` (a non-recursive
mutex plus a per-thread holder mark, lwipopts.h:51-52) passes it.

The rest of the resolve path is safe from any task: `lwip_getaddrinfo` (netdb.c) goes
through `netconn_gethostbyname_addrtype`, and the netconn/socket APIs take the core lock
internally. The single unlocked raw call on the crash path is the core's
`dns_clear_cache()` inside `hostByName`, reachable from every `connect(host, ...)` and
every explicit `hostByName` in the firmware.

## 3. Which change since f7553b56 opened this

None on the crash path. `git diff --name-only f7553b56..28813029` over the relay, SNTP,
network and transport paths is empty except `src/net/web_prefs.cpp` (prefs web UI):
`src/sys`, `src/agent/telegram.cpp`, `src/agent/transport_tls.cpp`, `src/agent/adapters`,
`src/agent/tg_archive.cpp`, `src/sfx`, `src/net/cloud_mint.cpp` are byte-identical; the
SNTP block of `src/agent/loops_subsystem.cpp` (`restartSntpClient`/`sntpTick`) is
identical; `platformio.ini` is identical (same pioarduino platform pin 55.03.39, same
solide-drivers v0.9.0), so the Arduino core and lwIP are the same build. The only
changes in the range are lib/core + lib/harness orchestrator work and the web UI.

So the panic is a latent race in the core, not a firmware regression: it needs (a) an
IP-state flip (the WIFIAP drop/rejoin does that), (b) a pending DNS entry whose
callback re-enters raw lwIP (SNTP's, kicked on the up edge), and (c) a host-based
connect from a non-TCPIP task inside that window. On `28813029` the boot/rejoin timing
put the relay's dial inside the window; on `c7961ec9` and `f7553b56` the same bench
sequence passed (`coverage/BENCH-RESULTS.md` rows: A03 PASS on c7961ec9 and f7553b56,
rejoin 3 s, no restart; FAIL crash-class on 28813029) because the interleaving did not
line up, not because the code differs.

## 4. Is v4.9.0 on Lumi exposed?

YES, under different timing. Lumi runs f7553b56 (v4.9.0), whose crash-path code is
byte-identical to the candidate's (section 3) on the same core pin, so the same race
exists there: any Wi-Fi drop/rejoin or AP-mode toggle while an SNTP DNS request is
pending, with the relay, tg_poll, the turn transport or any adapter dialing by
hostname, can panic the dialing task the same way. The A03 pass on f7553b56 is
evidence of a lucky interleaving, not of absence. The fix therefore ships to Lumi
through the normal OTA path with the candidate.

## 5. The fix (the class, not the instance)

`src/sys/net_util.h` gains the one locked seam, and the seam resolves with the RAW lwIP
DNS API, never with the core's `hostByName`:

- `resolveHostLocked(host, out[, waitMs])`: calls the raw `dns_gethostbyname()` under
  `LOCK_TCPIP_CORE()` (a raw API: it asserts the lock held but never takes it - the
  `webDnsReady` pattern in `src/agent/adapters/embeddings.cpp:81`). Cache hit returns
  `ERR_OK` immediately; on a miss the query is sent while the lock is held and
  `ERR_INPROGRESS` comes back, and the wait for the answer happens WITHOUT holding the
  lock (the answer arrives in the TCPIP thread, which needs the lock - the same shape
  the netconn layer itself uses, `api_msg.c` `lwip_netconn_do_gethostbyname`), bounded
  by `waitMs` on top of lwIP's own DNS retry timeout.
- `connectHost(c, host, port[, timeoutMs])`: resolves via `resolveHostLocked`, then
  connects by `IPAddress`, whose `connect()` runs no DNS at all
  (`NetworkClient.cpp:312` / `NetworkClientSecure.cpp:140,192` are the host overloads;
  the IPAddress overloads go straight to the socket).

Why not lock around `Network.hostByName` (the first attempt at this seam, reviewed and
rejected - see section 5a): `hostByName` resolves through the netconn API, which TAKES
the core lock itself (`lwip_getaddrinfo` netdb.c:418 -> `netconn_gethostbyname_addrtype`
netdb.c:495 -> `tcpip_send_msg_wait_sem` api_lib.c:1333 -> `LOCK_TCPIP_CORE()`
tcpip.c:446), and the core lock is a NON-RECURSIVE mutex taken with `portMAX_DELAY`
(`port/freertos/sys_arch.c:44` `xSemaphoreCreateMutex`, `:63` `xSemaphoreTake(...,
portMAX_DELAY)`; `lock_tcpip_core` is created by `sys_mutex_new`, tcpip.c:660). Holding
it across `Network.hostByName` self-deadlocks the calling task on a mutex it already
holds, freezing the whole network stack. Core locking is on in this build
(`CONFIG_LWIP_TCPIP_CORE_LOCKING 1`, `CONFIG_LWIP_CHECK_THREAD_SAFETY 1` in the esp32s3
sdkconfig; the A03 assert string is the core-locking branch of `LWIP_ASSERT_CORE_LOCKED`,
lwipopts.h:54).

With the seam resolving raw and connecting by IP, no task ever calls `hostByName`, and
`dns_clear_cache()`'s only caller in the whole stack is `NetworkManager.cpp:84` - so it
is never called from outside the TCPIP thread, on every path, not just the A03 one
(SNTP's own lookup runs in the TCPIP thread via `sys_timeout`, sntp.c:627/639).

All 25 host-based connect sites in `src/` route through `connectHost` (relay dial and
`httpsPostJson` in `src/net/relay_client.cpp`, `cloud_mint`, `sfx_sync`, `tg_archive`,
`telegram` tlsConnect, `transport_tls`, `http_multipart`, `tts_voices`, `audio_tts`,
`url_fetch` x2, `moderation`, `image_gen`, `provider_file_fetch`, `embeddings`,
`connectors` x2, `provider_verify` x6, `ota_update`), and the multipart pre-check's
resolve uses `resolveHostLocked`. IP-based connects (the loopback) stay direct.

Source guard: `tools/release_gate/check_lwip_core_lock.py` (style of
`check_critical_sections.py`), registered in `tools/release_gate/run_gate.py` host
checks. It fails the release on (1) any raw lwIP core API call (`dns_*`, `udp_*`,
`tcp_*`, `pbuf_*`, `netbuf_*`, `netif_*`, `ip_addr_*`, ...) outside a
`LOCK_TCPIP_CORE()` ... `UNLOCK_TCPIP_CORE()` region, (2) any bare `hostByName`
anywhere, the seam included, (3) any `hostByName` INSIDE a lock region (the
self-deadlock shape above), (4) any `connect(...)` whose first argument is not an
IPAddress-typed expression - a string, a member, a cast, any parenthesized expression
- unless it goes through `connectHost`, and (5) a `LOCK_TCPIP_CORE()` with no matching
`UNLOCK_TCPIP_CORE()`. Verified failing on the pre-fix tree: run against
`bench/wt/b500-28813029/src` it exits 1 with 26 findings (25 host-based connects + 1
bare hostByName), saved in `evidence/crash2/guard-on-28813029.txt` (old guard) and
`evidence/crash2/guard-on-28813029-reviewfix.txt` (this guard); on this branch it
passes (717 files, 3 lock regions). Host tests:
`tools/release_gate/test_lwip_core_lock.py` (14 tests, including the A03 dial shape
failing on its line, every raw API name failing outside a lock, the self-deadlock
shape, the parenthesized-first-arg connect, the unclosed lock, and the seam file
itself scanning clean under the full rules).

### 5a. Independent review fix pass (REVIEW-FINDINGS.json, 2026-11-04)

The orchestrator's review found three findings; all three were verified against the
pinned core/lwIP sources on disk and all three were real, so all three are fixed here
(no rejection):

1. CRITICAL - `hostByNameLocked` held the non-recursive core lock across
   `Network.hostByName`, which re-takes it via the netconn path: self-deadlock on the
   first outbound hostname connect. Verified chain on disk: sdkconfig
   `CONFIG_LWIP_TCPIP_CORE_LOCKING 1` + `CONFIG_LWIP_CHECK_THREAD_SAFETY 1`
   (framework-arduinoespressif32-libs esp32s3 qio_opi sdkconfig.h); lwipopts.h:51
   `LOCK_TCPIP_CORE()` = `sys_mutex_lock(&lock_tcpip_core)` + holder mark;
   port/freertos/sys_arch.c:44 `xSemaphoreCreateMutex()` (non-recursive) and
   `xSemaphoreTake(..., portMAX_DELAY)`; tcpip.c:660 creates `lock_tcpip_core` via
   `sys_mutex_new`; NetworkManager.cpp:100,104 -> netdb.c:418 `lwip_getaddrinfo` ->
   netdb.c:495 `netconn_gethostbyname_addrtype` (no cache fast path, no
   `LWIP_HOOK_NETCONN_EXTERNAL_RESOLVE` in lwipopts.h) -> api_lib.c:1333 ->
   tcpip.c:446 `LOCK_TCPIP_CORE()`. Fixed by removing `hostByName` from the seam
   entirely (raw `dns_gethostbyname` under the lock + connect by IPAddress); the guard
   now fails on the under-lock `hostByName` shape (rule 3) and on the seam connecting
   by host (rule 4 applies to the seam too).
2. MEDIUM - the class was not fully closed: `connect(host, ...)`'s internal
   `hostByName` (NetworkClient.cpp:312, NetworkClientSecure.cpp:140,192) could still
   run `dns_clear_cache` unlocked if the IP state flipped between the warm resolve and
   the internal resolve (the flip statics re-arm on any later interface change).
   Closed by the same fix: `connectHost` connects by IPAddress, so the core's internal
   `hostByName` never runs; no task calls `hostByName` at all.
3. LOW - the gate had two fail-open blind spots: a connect whose first argument starts
   with `(` was invisible to the host-connect rule (the old capture `[^,()]+` could not
   begin with a paren), and an unclosed `LOCK_TCPIP_CORE` exempted the rest of the file
   from the raw-lwIP rule (`_pair_end` returns end-of-text). Fixed: the connect capture
   now allows one level of nested parens (`c.connect((const char*)host, 443)` is
   flagged; a zero-argument `connect()` member still does not match), and an unclosed
   lock is itself a FAIL finding.

Failing-first evidence: the new tests were run on the pre-fix tree (head 774bafea) and
failed - 5 failed, 9 passed - saved in
`evidence/crash2/review-fix-tests-fail-first.txt`; after the fix, 14 passed
(`pytest tools/release_gate`: 228 passed).

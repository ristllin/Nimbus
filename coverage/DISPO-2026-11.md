## S10 - TEST DEFECT, fixed by lane CLAMP

The bench injected the clamp 402 through PROVFAULT and the device never resent capped. The fixture
body was byte-correct; the firmware's TEST seam answered the armed host before the transport, so the
resend loop never ran under PROVFAULT on any build. Lane CLAMP moved the scripted answer to the
transport's seat (commits 5966979a..5c3cfe4c, in this lane's base). Full cause and proof:
coverage/CLAMP-2026-11.md. Nothing for this lane to change; the candidate needs a rebuild + bench
rerun for on-glass proof, which is the bench's to do (no board here).

## D01 - TEST-SEAM DEFECT: the FAULT provider did not cover Z.ai

The D01 legs arm the FAULT provider to simulate a total LLM outage, but the dream still ran
(dream.last=ran): the head failed over to Z.ai and succeeded. The fault predicate in
src/agent/transport_tls.cpp (base lines 318-326) only matched api.openai.com, api.anthropic.com and
api.mistral.ai; Z.ai has been a first-class provider since lane MG, with two possible bases
(api.z.ai and open.bigmodel.cn), so the "total outage" was not total.

Fix (this lane): the host predicate moved to lib/core as
`nimbus::fault::providerOutageHost(host, zaiBase)` (lib/core/include/nimbus/fault.h,
lib/core/src/fault.cpp), and transport_tls passes `store::zaiBase()` so both Z.ai bases are covered
on the device. Failing-first class test
`test_provider_outage_cuts_every_llm_host_and_no_other` (test/test_fault/main.cpp) covers both Z.ai
bases and asserts non-LLM hosts are untouched: RED on the base
(evidence/dispo/fail-first-fault-provider-zai.log), green after the fix. The HIL legs that rely on
a total LLM outage (test_l58_dream_quiet, test_claim_check_bench, test_l16_compaction) now get one.

## H08 - TEST DEFECT: the squeeze leg pinned the wrong gate's wording

tests/hil/test_l71_combined_starvation.py leg 2 squeezes memory from the start of the turn and
expected SHORT_REPLY ("I'm short of memory right now..."), which is the DURING-turn gate
(lib/harness/src/turn_memory.cpp:10, engine.cpp:2808). A squeeze that is already active when the
turn starts correctly hits the CUM-404 ADMISSION gate instead (lib/harness/src/engine.cpp:2736-2741),
whose deliberate wording is different ("One moment, I'm finishing some background work and low on
working memory. Please resend in a few seconds."). The leg timed out waiting for wording the
design never sends in that state.

Fix (this lane): leg 2 asserts the admission reply exactly (ADMIT_REPLY, nothing loosened),
classify_end treats it as "refused", and the docstring says which gate each leg exercises. The
rerun2 ExpectTimeout on 'FAULT sram_ballast' is the known ballast-starves-console flake (attempt 1
passed); not graded.

## H09 - TEST DEFECT: the leg pointed at a path the product refuses by design

The bench graded FAIL because turn 1 made no keyed files.append on qw3-bench/food-log.csv. That is
the one-food-log invariant working as designed, not a head fault: lane FOOD (3e9230d3, in the
candidate) made the device refuse a keyed append or artifact.save to any food-log-named CSV outside
project food - `secondFoodLogRefusal` (lib/core/src/orch_food_ledger.cpp, device call sites
src/agent/files_subsystem.cpp:2028 and :2073) - with a message that names the one ledger. The QW3
leg predates that invariant and still asked the head to log to qw3-bench/food-log.csv, a path the
product can never let it write: the leg was unpassable by construction, exactly like S10.

The live rate run (evidence/dispo/rate-legs.log, dispo-h09, 5 reps on the lab rig) shows the real
behavior: 4/5 the head tried the named file, was refused, and wrote the dinner to the one ledger
with an honest reply naming where it went; 1/5 the head claimed the log without any tool call (a
model-choice miss a client would notice - noted below, not the bench FAIL's shape).

Fix (this lane): the QW3 leg runs on the one ledger (tests/hil/test_qw3_food_log_midnight.py,
PROJECT/NAME = food/food-log.csv). The grader (qw3_food_grade.py) is path-agnostic and its seed
header is already the ledger header; the seed upload is the owner's hand through the web API, which
the refusal does not gate. The midnight, correction and totals logic the leg exists to replay is
unchanged - it now replays on the ledger the product actually keeps.

## H14b - TEST DEFECT: the kit's first console command after reset is eaten

The probe ($EV/H14b/probe-album.log) showed the FIRST console command after the fixture's
reset+reopen is always eaten, whatever its shape (album-first, text-first, long-HISTADD-first: all
dt=25.1s, reply=''), and every later command works. Root cause: pumpBoot()
(src/test_console.cpp:2300-2325) answers PING with "PONG (boot console)" during setup() and discards
every other line, so the kit's resync PING can be answered by the boot pump while the full console
is not up. Album failed only because parametrize's sorted(PAGES) made it the session's first
command.

Fix (this lane): `Device.wait_console_ready()` (tests/hil/device.py) PINGs until it sees a PONG
that is NOT "(boot console)" and pushes back any non-reply lines it consumed; the device fixture
(tests/hil/conftest.py) calls it right after dev.reset(). No assertion weakened; the kit now waits
for the real console instead of racing it.

## F03 - MODEL-CHOICE VARIANCE: which targets the head stores

The bench seeded food/plan.md ("Daily target: 2,400 kcal and 155 g protein") and asked "how much
protein is left today?" then "and calories?". The head stored the protein target (keyed, with its
source) and did not store a kcal target; the reply-2 "(Correction:" line was the product's own
claim-check honesty path (lib/harness/src/claim_check.cpp, the "Bench F03" block) bouncing an answer
whose citation states unstored targets. Same clause on all three bench shas.

Rate over repeated real runs (evidence/dispo/rate-f03.log, dispo-f03, 5 reps, NIMBUS_DISPO_REPS=5,
the lab rig against real providers): protein target stored 5/5, both targets 0/5, neither 0/5,

column only; the re-run is the recorded evidence.) Would a client notice? The client gets an
honest "I don't have a calorie target stored" reply and the kcal figure from the plan when asked;
the protein target, once stored, is durable. No write-path fault: every rep's keyed append landed.

## H18 - MODEL-CHOICE VARIANCE: the spawn leg's provider card

spawn tool takes an optional provider/model hint (lib/core/src/orch_session_tools.cpp:36,41) and the

The CUM-887 stepdown path itself is host-proven (test/test_harness_wire_mistral/main.cpp:1498-1612:
the recorded 3004 body moves the turn to mistral-medium-latest and the reply names it) and
live-proven on this lane: evidence/dispo/mg-live.log (the lab's mg-live leg, mistralDispatch on
mistral-large-4-0 with the web_search connector). The live run also showed the stepdown is

(no 3004), so the sub ran with its tools where it was asked and answered with sources - the leg's
verdict had pinned the stepdown's observable (the reply naming mistral-medium-latest), which only
appears when the provider actually refuses; the leg now passes on either outcome (the sub keeps its
tools), because a 3004 is provider weather, not the device's choice. Client impact: none - the
bench's helper ran, the web search worked, the artifact was sourced.

## A08 - TEST/MEASUREMENT DEFECT: three measurement faults, no product signal

tests/hil/bench_rows.py row_a08 reported a "drop" of 4294963063 B. Three faults in the
measurement, none a product defect:

1. The before-snapshot read pollStackMin before it was ever set, catching the unset sentinel
   0xFFFFFFFF and reporting 4294963063 B as a drop.
2. mem.lowWater is a since-boot monotonic minimum (src/sys/heap_watch.cpp:252, pumped at 1 Hz);
   A02's state file was from the PRE-crash boot (A03 crashed the unit), so the comparison was
   cross-boot and contaminated by rows A03-A07. The same script passed on f7553b56 only because
   that session ran A02 then A07/A08 back-to-back on one boot.
3. A07 was graded BLOCKED (the HISTADD approximation cannot reach the overflow: history
   summarized, no "turn fit: left out"), so A08 measured a turn that never trimmed.

The absolute value it did measure (28,092 B) is 3.5x above the 8,000 B floor, allocFails 0, no
panic. Fix (this lane): row_a08 guards the sentinel (unmeasurable, not a drop), guards the boot
number (the state JSON carries boot.n; a cross-boot lowWater comparison is invalid), and grades
BLOCKED, not FAIL, when A07 did not trim.

## SOUND-AT-BOOT - NO PRODUCT DEFECT: sfxVol 0 is true silence

Read from code, end to end:

- The boot chime fires at src/main.cpp:4684 (::sfx::fire(Ev::Boot), the "boot complete chime" at
  the end of setup(); a plain reset re-runs setup()).
- fire() gates on the sound level (src/sfx/sound_fx.cpp:293-295 -> lib/core/src/sfx_map.cpp:69-72
  shouldPlay: level > kLevelNone and >= rank; Ev::Boot's orchestrator rank is kLevelMedium,
  sfx_map.cpp:20). With sfxLvlO=0 the chime is not even queued.
- Master volume applies per sample (solide-drivers src/device/audio.cpp:70 setVolume: sfxVol=0 ->
  s_vol256=0; :263 (mono[i]*s_vol256)>>8 -> all-zero samples). With sfxVol=0 the speaker gets true
  silence even if a chime queues. applyConfig applies the stored volume at boot (sound_fx.cpp:262,
  189).
- Defaults on a factory-fresh or NVS-wiped board: sfxVol=50 (src/agent/store.cpp:1169),
  sfxLevelOrch=2 (store.cpp:1167) - the chime DOES play at half volume on the first boot after a
  wipe, and it fires in setup() before any console input can land, so a wiped board chimes once
  before SFXVOL 0 can be set.
- Selftest forces s_vol256=256 (audio.cpp:535) but only from a user-initiated SELFTEST, the web
  test or relay loopback (src/hw/selftest.cpp:130, src/net/webui.cpp:3976,
  src/test_console.cpp:968) - never at boot.

Verdict: with sfxVol=0 persisted, a Nimbus board makes no sound at boot or reset. The owner's
"startup sounds" were the first boot after a wipe, at the default volume, before the setting was
restored. No fix; the behavior is correct as designed.
